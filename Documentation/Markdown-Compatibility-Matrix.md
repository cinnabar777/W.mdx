# Markdown compatibility matrix

This is the working, evidence-backed compatibility gate for opening, importing, rendering, and exporting Markdown dialects. “Verified” means the named fixtures and operations pass; it does **not** mean every feature in a dialect's entire ecosystem is supported. Unsupported or untested cases must stay visible here instead of being described as fully compatible.

Wmdx remains the app's editable internal Markdown form, but converting through Wmdx is not the HTML-compatibility gate. HTML import and HTML export are tested independently for each dialect. A Markdown → HTML → Markdown round trip is supplemental only: it cannot show what arbitrary HTML input loses or what HTML export omits.

## CommonMark is the prerequisite baseline

CommonMark is **not yet certified as fully implemented in Wmdx**. Editor parsing still uses CodeMirror/Lezer and Wmdx-specific layers; CommonMark HTML export now uses the pinned `commonmark@0.31.2` reference renderer, and standard reference-rendered CommonMark HTML import uses Turndown before the existing Wmdx conversion. The new independent gate is `web/test/commonmark-html-parity.test.cjs`; its initial run (`43916140913`, before these adapters) found 34/575 export-rendering differences and 72/575 HTML-import round-trip differences. Run [43939035662](https://github.com/cinnabar777/W.mdx/actions/runs/43939035662) on commit [61ce6fca](https://github.com/cinnabar777/W.mdx/commit/61ce6fca2c5720eca5aad50453f79d66c3c2d1a5) passed all 575 non-raw-HTML cases in both reference HTML directions (1,152/1,152 Node tests); this closes the pinned core HTML parity gate, not full CommonMark editor behavior or the separate raw-HTML breadth gate. The other 77 raw-HTML examples have selected semantic checks and explicit security-loss cases, not exhaustive HTML behavior. The complete editor-view/caret/scroll gate is also still open. See `web/test/commonmark-spec.test.cjs`, `web/test/commonmark-html-parity.test.cjs`, and `Documentation/Markdown-Element-Compatibility-Test-Plan.md`.

Therefore the compatibility order is: first close CommonMark's runtime parsing, rendering, and supported editing behavior in Wmdx, with intentional active-HTML security restrictions explicitly documented; next prove CommonMark HTML export and independent HTML import; then add GFM and Obsidian as tested dialect extensions and apply the same independent HTML gates to their additional features. Existing round-trip coverage is useful evidence, but does not move these prerequisite gates to “complete.”

## Independent HTML import/export gate

For every supported Markdown feature, record **HTML export** and **HTML import** separately. Do not infer either result from a Markdown self-round-trip or from HTML generated by the same app.

| Direction | Start from | Required check | What to record |
| --- | --- | --- | --- |
| Markdown → HTML export | Individual CommonMark, GFM, or Obsidian feature cases, plus complete documents | Confirm every feature that the source dialect can represent in HTML appears with equivalent meaning in the output DOM. Compare against the dialect's reference parser/renderer where available, not only Wmdx output. | Preserved semantics and structure; omitted or changed content; security filtering; whether dialect-only details need explicit HTML metadata. |
| HTML → Markdown import | Independent HTML fixtures, including hand-authored and known-good exporter output—not only this app's own HTML | For each selected target dialect, confirm every HTML construct that dialect can represent is imported with equivalent meaning. If no native syntax exists, preserve safe HTML or report a specific loss; never silently discard it. | Imported feature and target spelling; retained raw HTML or metadata; warnings and intentional security losses; full-document and trailing-content checks. |
| Markdown → HTML → Markdown | A supplemental integration route after both directions above are covered | Check semantic stability and documented losses across the combined route. | This catches interaction regressions, but does not replace either independent direction. |

Use established dialect parsers, renderers, and import/export implementations as reference behavior and candidate components. First identify what they already support, their license and runtime constraints, and where their behavior differs from Wmdx; implement custom adapters only for demonstrated gaps. Mark a feature complete only when its import and export evidence is independently recorded.

## Faster implementation without fake coverage

Use a small, change-aware test gate rather than rerunning every combination after every edit:

1. **Feature change:** run the one-feature parser/serializer test, independent HTML input and output cases for that feature, and only its affected editor interaction test.
2. **Shared parser, HTML mapping, or serializer change:** run the relevant upstream CommonMark/GFM corpus and the affected cross-dialect conversion slice.
3. **Integration or release gate:** run all dialect HTML ledgers, complete fixture archives, and the broader conversion suite. Run the full editor interaction/device matrix only when shared editor behavior changes or before a release.

The full compatibility suites remain required evidence at the integration/release gates; they are not repeated as a substitute for a focused test on every small change. Reuse a licensed parser or converter when it already passes the relevant feature cases, and write an adapter only for a measured mismatch. Keep every known loss listed; a faster gate must not silently turn pending rows into passes.

### Document Appearance requirement for added syntax

When compatibility work adds a dialect feature Wmdx does not already support, add a clearly named section for that feature under **Document Appearance**, with its actual display controls and defaults. For example, Mermaid support needs controls for whether diagrams render and how their presentation behaves; when rendering is disabled or unavailable, the original fenced source must remain available. Tests must change each new setting through its real control, verify its effect, and verify reset/default behavior. A parser that merely preserves syntax does not satisfy this rendered-feature requirement.

## Known exclusions and next gates

- CommonMark raw HTML interoperability remains separate from native Markdown parsing. All 77 upstream HTML cases are individually classified, with semantic-preservation or warning-checked intentional security-loss assertions and zero pending cases. This closes the pinned examples only, not every possible HTML nesting or import/export combination.
- All 575 parser-comparable CommonMark core cases pass rendered-semantic round trips through Wmdx, GFM, and Obsidian, including the 10 nested-emphasis cases previously known to fail. This does not close the separate raw-HTML track or the all-view interaction gate.
- Escape minimality now has per-backslash checks for 523 CommonMark core cases without authored escapes/bracket collisions, plus focused link, resource, media, table, footnote, and Wmdx-specific cases. Authored-escape and bracket/link-collision corpus cases, the remaining serializer branches, and all-view interactions still need reconciliation; do not mark Markdown flavor compatibility complete on this basis.
- GFM's nine-tag raw-HTML tagfilter is applied during HTML export. Raw HTML is still not fully rendered or converted identically in every editor view.
- The Obsidian fixture set is intentionally curated, not a claim of complete Obsidian compatibility. Note transclusion is now preserved as literal escaped text with an explicit warning when exported to CommonMark/GFM; it is not embedded there. Inline footnotes export as GFM reference footnotes with generated collision-safe labels; CommonMark retains inline source with a warning. GFM rendered/reader parity remains unverified. Plugin-defined syntax and other app-only features still need explicit support decisions and fixtures.
- The web export bridge now renders semantic HTML from the full Markdown source independently of editor mode, and browser tests verify it does not export CodeMirror markup. Android document-provider asset reads, separate CSS, and post-fix MHTML TOC-link behavior still need device acceptance.
- MHTML import now honors the MIME `start` root and `Content-Base`; broader real-world archive samples and CSS-dependent layouts still need fixtures.
- HTML/MHTML conversions preserve tested semantic content and related media bytes, but source-only distinctions can change: CommonMark has no native task list, CommonMark pipe tables are not standard, and arbitrary HTML does not carry Obsidian wikilink/callout identity unless the app adds metadata. Markdown link titles are retained; image tooltip titles and custom CSS have no general Wmdx field, so image title markup remains raw HTML with a warning.
- LaTeX, AsciiMath, Typst, and a WYSIWYG equation editor are not integrated. Obsidian inline/display math is kept literal in the tested conversion and HTML-export paths so Markdown emphasis cannot rewrite it, but equations are not typeset. This verifies syntax preservation, not math rendering or editing behavior.

Do not mark a row fully compatible just because import and export return text. The acceptance test must compare rendered meaning, verify the entire document including its tail, and record any warning or intentional loss.
